## Vision

### 10x Check
Instead of building all 9 modules bottom-up before any human touches the product, flip to iterative vertical slices. Each version is a working webapp testable on a phone. v0 ships in ~30min CC (Claude Code) time using the existing pose pipeline. Feedback loops at every milestone prevent building the wrong thing.

### Platonic Ideal
Film your squat, get world-class coaching feedback on your phone in under 10 seconds, powered by thousands of real coaching interactions from the lifting community. Each iteration gets closer to this.

## Accepted Scope (added to this plan)

### v0 — Proof of Life (CC: ~30min)

**Infrastructure:** FastAPI + uvicorn. No relational database. No Redis. No Celery. Videos persisted via `blob/` (the `LocalBlobStorage` filesystem backend shipped in PR #1).

**Scope:**
- FastAPI app (`backend/src/autocoach/api/`) with Jinja2 templates
- HTML upload form with camera capture button (`capture="environment"`)
- Loading animation (inline JS spinner during 3-6s processing wait)
- Video duration check: client-side JS reads video metadata, server-side enforces ≤30s
- Video size limit: 100MB enforced by FastAPI middleware
- Persist uploaded video via `blob/` storage (`videos/{uuid}.mp4`)
- Run pose pipeline **synchronously** — route defined as `def` (not `async def`) so FastAPI auto-runs in thread pool. Acceptable for 1-3 concurrent users.
- HTML results page rendered in the same request (in-memory — no DB needed)
- **Squat-only** — lift_type hardcoded to "Squat". Other lifts added in v0.5.

**Results page shows:** `min_knee_angle`, `min_hip_angle`, `max_back_angle`, `view_confidence`, `dominant_side`, `phase_labels`. All angles in degrees. **Intentionally raw** — v0 validates the pipeline works on real user videos. Interpretation (grades, cues) comes in v0.5. Error pages use the same Jinja2 template system with styled HTML, not raw stack traces.

**Error handling:**
- `PipelineError` (front view rejected) → error page: "Re-film from the side"
- `PoseExtractionError` (bad video) → error page: "Could not process video — try a different recording"
- Video too long / too large → error page with specific message
- Generic exception → error page: "Something went wrong. Try again."

**Deployment:** Local dev via `uvicorn`. For phone testing, expose via ngrok or similar tunnel. Production hosting (Railway/Fly.io) is a v1 concern.

**CC time breakdown:** FastAPI app scaffold (~10min) + HTML templates (~10min) + blob integration + pipeline wiring (~5min) + error handling + validation (~5min).

### v0.5 — Form Grade (CC: ~45min)

**Infrastructure additions:** None. Still no DB/Redis/Celery.

**Scope:**
- Scoring module (`scoring/scorer.py`): takes `BiomechanicalFeatures` → `FormScore(overall_grade: str, criteria: list[CriterionScore])`. Grades A-F per criterion. **Squat:** depth (hip crease vs knee), knee tracking, back angle — most refined. **Deadlift:** hip hinge angle, back angle — meaningful from BiomechanicalFeatures. **Bench press:** limited to back angle + elbow angle proxy — scored with caveat "Bench scoring is experimental (angles measured from side view of a horizontal body)." All three lifts score-able; bench is honest about limitations.
- Rule-based coaching cues: map score thresholds to cue strings (e.g., C on depth → "Try to get lower — hip crease should go below your knees")
- Lift type selector dropdown (Squat/Bench/Deadlift) on upload form — passes `lift_type` to pipeline.
- Visual angle gauges: colored bars (green/yellow/red) for each scored metric
- Results page upgraded: letter grade prominently displayed + per-criterion breakdown with gauges + coaching cues

**CC time breakdown:** Scoring module + tests (~20min) + coaching cues data (~10min) + HTML/CSS upgrades (~15min).

### v1a — Async + Persistence (CC: ~1.5hr)

**Infrastructure additions:** Redis (broker, already in docker-compose), Celery worker process, PostgreSQL (already in docker-compose, needs Alembic setup).

**Scope:**
- **PostgreSQL persistence:** `analyses` table (video_id, user_uuid, lift_type, form_score, coaching_json, created_at). Alembic for schema migrations.
- **Celery worker** (`worker/tasks.py`): `process_video(features_json, video_key, user_uuid)` — for now just persists scoring results to PostgreSQL (LLM/overlay added in v1b). Redis broker.
- **JSON API endpoints** alongside HTML pages: `POST /api/v1/analyze` (returns task_id + instant tips from scoring), `GET /api/v1/status/{task_id}` (poll), `GET /api/v1/results/{video_id}` (persisted results)
- **Two-phase response:** API runs pose+scoring synchronously (3-6s), returns instant rule-based tips in the HTTP response. Then queues Celery task to persist results.
- **HTML polling page:** JS polls `GET /api/v1/status/{task_id}` every 2s, shows progress, auto-loads full results when complete.
- **Shareable results URL:** `GET /results/{video_id}` — stable URL. Not the form card image (that's v2). Just a link you can text to a friend.
- **Anonymous UUID system:** generate UUID on first request, store in HTTP-only cookie. Included in v1a (not deferred to v1.5) because the worker needs `user_uuid` to write to the analyses table.

**Note on BiomechanicalFeatures serialization:** The model uses `list[float]` and `str` fields only (no numpy arrays). `model_dump_json()` works directly.

**CC time breakdown:** PostgreSQL + Alembic setup (~20min) + Celery worker (~20min) + JSON API + polling (~25min) + UUID system (~15min) + tests (~10min).

### v1b — LLM Coaching + Overlay (CC: ~2-3hr)

**Infrastructure additions:** Qdrant (for RAG, already in docker-compose). LLM API keys (env vars).

**Prerequisite:** Populate Qdrant with scraped Reddit data. Run existing scraper + embedding pipeline before v1b launch. If corpus is empty, LLM coaching works without RAG (falls back to biomechanics-only prompts).

**Scope:**
- **LLM coaching** via litellm: provider chain Claude Haiku → GPT-4o-mini → Gemini Flash. Structured JSON output (schema: `{cues: [{text, severity, related_angle, frame_idx}], summary, safety_warnings}`). Fallback to rule-based if all fail. Credentials via env vars (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`).
- **RAG retrieval:** uses existing `rag/store.py` + `rag/embeddings.py` (already built, 13 tests) to find similar lifts from scraped Reddit data in Qdrant. RAG comment sanitization strips instruction-like patterns before LLM prompt.
- **Overlay module:** extract 3-5 keyframes via OpenCV seek-based extraction (not full decode), draw skeleton overlay with color-coded angles, return annotated PNGs via blob/. **Note:** blob `get_url()` returns filesystem paths; API must mount blob root as static files for keyframe image URLs to work in HTML.
- **Extend Celery worker:** add RAG + LLM + overlay stages to `process_video` task. Persist coaching text + keyframe URLs to analyses table.
- **Results page upgrade:** show LLM coaching text + annotated keyframe images alongside scoring grades.

**CC time breakdown:** LLM coaching module + tests (~45min) + overlay module + tests (~45min) + RAG integration + sanitization (~20min) + worker extension (~15min) + results page upgrade (~15min) + Qdrant data population (~10min).

### v2 — History & Social (CC: ~1.5hr)

**Infrastructure additions:** None new. Extends PostgreSQL schema.

**Scope:**
- Analysis history page: `GET /history` — list of past analyses for this UUID (from v1a), sorted by date, grouped by lift type
- Progress tracking: show grade trend per lift type (e.g., "Squat: C → B → B+"). Grades are A-F (no plus/minus in v0.5 scoring; plus/minus is a v2 display refinement using score deltas).
- Shareable form card image: PIL/Pillow template with grade + metrics + skeleton keyframe. Sized for sharing (1200×630). Distinct from the shareable URL in v1a — this is a rendered image.

**CC time breakdown:** History page + query (~20min) + progress display (~15min) + form card image (~45min) + tests (~10min).

## Key Architecture Decisions

### v0: Synchronous Processing
The pose pipeline takes 3-6s. For v0 with 1-3 concurrent users, synchronous processing is fine. Define upload route as `def` (not `async def`) so FastAPI runs it in a threadpool automatically, avoiding event loop starvation. No Celery, no Redis, no worker.

### v0→v1a Transition: Adding Async + Persistence
v1a adds Celery, Redis, PostgreSQL. The worker initially just persists scoring results — no LLM or overlay yet. This validates the async architecture (task queuing, polling, result retrieval) in isolation before layering on LLM complexity.

### v1a→v1b Transition: Adding LLM + Overlay
v1b adds the expensive features (LLM coaching, RAG retrieval, overlay generation) on top of the proven async infrastructure. If LLM providers or Qdrant break, the async architecture still works.

### HTML Pages + JSON API (v1a)
v0-v0.5 serve HTML pages directly from FastAPI (Jinja2 templates). v1a introduces JSON API endpoints (`/api/v1/*`) for task polling and future frontend migration, while keeping the HTML pages for direct phone access. Both share the same backend logic.

### Results Persistence (v1a)
v0-v0.5 render results in-memory on the same request (no persistence). v1a introduces PostgreSQL for results storage (needed for shareable URLs and async worker results). Alembic manages schema migrations. UUID system also added in v1a (worker needs user_uuid to write analyses table).

### Blob Path Resolution (implementation note)
`PosePipeline.process()` takes a `Path`. `LocalBlobStorage.get_url()` returns a string of the absolute filesystem path. For v0, the API can use `Path(blob.get_url(key))` to pass to the pipeline. For v1b overlay keyframe images, the API must mount the blob root directory as FastAPI `StaticFiles` so that image URLs are HTTP-accessible in HTML pages.

## Reviewer Concerns

Issues flagged by spec review and outside voice, deferred to `/plan-eng-review`:
1. **v0 threadpool saturation:** FastAPI default threadpool is 40 threads. Under heavy load (>40 concurrent 6s requests), new requests queue silently. Acceptable for testing; document the limit.
2. **BiomechanicalFeatures serialization round-trip test:** Add a unit test asserting `json.loads(features.model_dump_json())` succeeds — validates the no-numpy assumption.
3. **v1b LLM output schema validation:** The `CoachingResponse` Pydantic model needs full definition during eng review.
4. **Overlay keyframe extraction approach:** OpenCV seek-based extraction specified; exact frame selection strategy (worst score frame, best frame, deepest point) deferred to overlay module design.
5. **v2 form card image design:** PIL/Pillow text rendering and font loading are fiddly; CC time estimate updated to 45min.
6. **v0 CC time estimate is optimistic:** Outside voice flagged mobile browser quirks (iOS Safari file picker, video metadata API) that add friction. Realistic estimate: 60-90min, not 30min.
7. **Blob path wiring:** `PosePipeline.process()` takes `Path`, `blob.get_url()` returns `str`. Resolved via `Path(blob.get_url(key))` — but this couples API to blob's internal path format. Acceptable for `LocalBlobStorage`; S3 backend will need different wiring.
8. **Overlay per-frame color coding:** Requires looking up angle thresholds from scoring config at each keyframe. Design decision: overlay module depends on scoring thresholds config, not the scoring module itself.
